# Security policy

## Keeping sensitive data out of the repository

This is a public portfolio project. Before any code is committed or merged, the changes are scanned for:

- secrets and credentials: passwords, tokens, API keys, AWS access keys, private keys and certificates
- confidential information
- personal data (PII) such as personal email addresses and names
- AWS account IDs, and real resource names or endpoints that identify an account
- files that should never be committed: `.env`, `*.pem`, `*.tfstate`, `*.tfvars` and saved Terraform plans

Anything found is removed before the commit or merge. The scan runs at three points: the pre-commit hook (staged changes), the `Scan for secrets and sensitive data` pull request check (every commit in the pull request and all tracked files, required before merging to `main`), and by hand on a whole branch before pushing or merging (`python3 scripts/secret-scan.py --all-tracked`). `.gitignore` excludes the file types above.

**Automated check:** `scripts/secret-scan.py` runs as a git pre-commit hook and blocks the commit on a match. It reports the rule, file and line with a
redacted snippet, never the value. Enable it once per clone:

```bash
./scripts/install-hooks.sh
```

Other modes: `--all-tracked` scans every tracked file, `--range BASE..HEAD` scans the lines added by a range of commits, and `--self-test` checks the rules. A reviewed
false positive can be accepted by putting `secret-scan: allow` on that line. To block values specific to you (your account ID or email), list them one per line in
`~/.config/secret-scan/literals`; that file stays outside the repository.

**Current limit:** the hook is local, so it can be skipped (`--no-verify`) or never enabled. The `Scan for secrets and sensitive data` pull request check re-runs the scan on every commit and every tracked file and is required for `main`, so it is the real backstop; GitHub secret scanning with push protection is a second layer. The details and known limits are in [docs/SECRET_SCANNING.md](docs/SECRET_SCANNING.md).

## How secrets are handled in the design

- The database password is generated by Amazon RDS and stored in AWS Secrets Manager. It is never in code, in the image, in the task definition or in Terraform variables or state.
- The app reads the secret itself at runtime, using its task role (one permission, on that one secret), and fetches it again after RDS rotates it. No environment variable holds the password. See [docs/Secrets.md](docs/Secrets.md).
- `.env.example` holds placeholders only. Real values live in a git-ignored `.env` or in AWS.

## Reporting a vulnerability

Please report a vulnerability privately through GitHub's private vulnerability reporting for this repository rather than a public issue.
Include what you found, how to reproduce it and the impact. Please do not test against any deployed environment without permission.

## Automated security scanning

Every pull request is scanned for secrets, code weaknesses (Semgrep), vulnerable libraries (`npm audit`, Trivy), the container image and Dockerfile (Trivy) and insecure Terraform (Checkov), and all of these must pass before merging to `main`. Dependabot proposes weekly updates for Actions, npm packages, base images and Terraform providers. Details and the exact tools: [docs/CICD.md](docs/CICD.md#security-scans).
